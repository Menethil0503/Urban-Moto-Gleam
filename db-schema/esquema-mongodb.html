📖 Cómo leer este documento. En MongoDB no hablamos de tablas sino de colecciones, y de filas sino de documentos (tipo JSON/BSON). Cada colección se muestra en dos vistas: una tarjeta resumen y una tabla detallada con campo, tipo, índice y descripción. Las relaciones 1:N se implementan con referencias (un campo que guarda el ObjectId del documento padre) o con datos embebidos (sub-documentos). El proyecto no tiene login, por eso los datos del cliente se guardan denormalizados dentro de reservas.

5. Índices de la base de datos

🔒 Índice clave: control de sobrecupos

  • reservas → { fecha: 1, hora: 1 } único y parcial sobre activa: true (nombre: cupo_unico_activo).
  • Garantiza que un día y una hora solo admiten una reserva activa.
  • Al cancelar una reserva, activa pasa a false y el cupo se libera.
  • Si dos personas reservan el mismo bloque a la vez, MongoDB rechaza la segunda (error 11000) y la API responde 409 Conflict.

⚡ Otros índices

  • reservas.codigo → único
  • reservas.placa → búsqueda por moto
  • reservas.estado + fecha → compuesto, agenda del panel
  • reservas.createdAt → orden descendente
  • paquetes.activo, paquetes.categoria
  • faqs.activo, faqs.categoria
  • testimonios.aprobado
  • proceso_lavado.paso → único
  • conversaciones.sesionId → único
  • mensajes.leido

6. Decisiones de diseño

📄 Documentos y relaciones

  • Referencias (ObjectId) para las relaciones 1:N (paqueteId, usuarioId, atendidoPor).
  • Embebido en conversaciones.mensajes[], paquetes.caracteristicas[], company.redesSociales[] e company.imagenes, porque siempre se leen junto al documento padre.
  • Denormalización de los datos del cliente en reservas (no hay login).

💰 Precios y fechas

  • El precio se guarda como número + moneda + notaPrecio, para poder consultar “servicios entre $50.000 y $120.000”.
  • fecha se guarda a medianoche UTC para evitar corrimientos por zona horaria (Bogotá es UTC−5).
  • La hora va aparte como texto "HH:MM", con 8 bloques disponibles por día.

🛡️ Integridad y auditoría

  • unique en reservas.codigo, proceso_lavado.paso, conversaciones.sesionId.
  • Validación de tipos en el esquema Mongoose (requeridos, min, enum de estados).
  • createdAt / updatedAt automáticos en todas las colecciones.

🧩 ¿Por qué MongoDB y no SQL?

  • El contenido ya vivía como documentos JSON en data.json: encaja de forma natural.
  • Los datos del taller son flexibles (cada paquete con sus propias características, cada moto con su configuración).
  • Las relaciones son pocas y simples (1:N), ideales para referencias en lugar de JOINs.

📦 Qué guarda cada interacción

  • BookingModal → reservas (con datos del cliente y de la moto).
  • ContactSection → mensajes.
  • FaqChatbot → conversaciones (mensajes embebidos).
  • Panel /admin → lee reservas y cambia su estado.

🔔 Notificación al cliente

  • Al crear la reserva, el servidor envía al cliente un WhatsApp con día, hora, nombre, moto, placa y servicio.
  • Se usa whatsapp-web.js (sesión de WhatsApp Web vinculada por QR) — es una solución de demo, no de producción.
  • El resultado del envío se registra en reservas.whatsappEnviado / whatsappError.
